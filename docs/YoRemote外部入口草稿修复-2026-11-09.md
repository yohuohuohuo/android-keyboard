# YoRemote 0.1.1：外部入口恢复草稿

日期：2026-11-09。本轮仅修复外部入口清空 task 导致草稿丢失的 P2，沿用本地授权，不提交或推送，不清理旧设置项。

## 原因和最小改动

通知“打开”、快捷设置和桌面组件都使用 `NEW_TASK | CLEAR_TASK` 启动 MainActivity。草稿与待核对原文由该 Activity 的 RemoteViewModel 保存在内存中，清空 task 会结束旧 Activity，因此外部入口本身就能让这些内容丢失，不需要等到进程回收。

三处入口统一使用 `ACTION_MAIN` 与 `NEW_TASK | CLEAR_TOP | SINGLE_TOP`。MainActivity 的 Manifest 保持默认 `standard`，没有新增 Activity、全局 launchMode、保存文本到磁盘、队列或自动重放。`SINGLE_TOP` 使 `CLEAR_TOP` 找回默认模式的 MainActivity 时走原实例 `onNewIntent()`；只删除 CLEAR_TASK 或只使用 CLEAR_TOP 都不满足要求。依据：[Android Intent 官方规则](https://developer.android.com/reference/android/content/Intent#FLAG_ACTIVITY_CLEAR_TOP)、[任务与返回栈](https://developer.android.com/guide/components/activities/tasks-and-back-stack)。

修改位置：

- `BluetoothHidService.createOpenApplicationPendingIntent()`：同时覆盖未连接与已连接通知的“打开”动作。
- `QuickSettingsTileService.onClick()`：覆盖 API 34+ PendingIntent 和此前 Intent 分支。
- `MediaControlWidget.getStartActivityIntent()`：同时供组件未连接“连接”按钮与已连接“打开”按钮使用。

通知 PendingIntent 还存在直接相关的旧令牌复用：只更换 flags 时，已缓存的旧 PendingIntent 仍可能带回 CLEAR_TASK。新增一条保留旧通知令牌的回归先失败，再用固定 ACTION_MAIN 区分旧的空 action 令牌，不取消其他入口持有的 PendingIntent。参见 [PendingIntent 官方匹配规则](https://developer.android.com/reference/android/app/PendingIntent)。

## 回归证据和边界

新增 `ExternalEntryTest.kt`，首批 7 项旧行为均失败，失败值都是实际生产入口 Intent 的 CLEAR_TASK 位 `32768`；修改三行标志后，7 项通过；随后针对旧 PendingIntent 追加第 8 项失败回归，加入 ACTION_MAIN 后，原 36 项与新增 8 项合计 44 项通过。证据保存在 `artifacts/yoremote-external-entry-evidence/entry-red.log`、`entry-red-results/` 和 `entry-green.log`、`retained-pending-red.log`、`all-green.log`，修复前追加补丁也已单独备份。修复前 APK `artifacts/yoremote-0.1.0-debug.apk` 保留，SHA-256 为 `3d6d7772b563a1b55b38ad64d88949bc8f82aa66c6c1bce4cad284aa4e4b41fe`。

测试不是只操作同一个 ViewModel 的 pause/resume：

| 场景 | 实际检查 |
| --- | --- |
| 通知 × 普通草稿 / 部分发送中止 | 从生产通知动作中取出 PendingIntent，验证其保存的 Intent 与 send() 实际派发的 Intent 一致 |
| API 36 磁贴 × 两类草稿 | 执行生产 onClick()，捕获传给 startActivityAndCollapse 的 PendingIntent，并检查实际派发结果 |
| 桌面组件 × 两类草稿 | 检查组件两个启动按钮共用的实际启动 Intent；Glance RemoteViews/启动器封装不在本次模拟测试范围 |
| API 28 磁贴 | 执行生产 onClick()，检查旧版 Intent 分支的实际派发结果 |
| 默认 launchMode | 通过 PackageManager 读取实际 Manifest，确认是 standard；逐入口检查 NEW_TASK、CLEAR_TOP、SINGLE_TOP 及无 CLEAR_TASK |
| 原实例恢复 | 使用真实 MainActivity 和真实 BtRemoteApp，退后台后把已验证入口 Intent 显式交给 onNewIntent，再恢复前台；检查 Activity、ViewModel 对象身份、当前 Tab、普通草稿或“原提交文本 + 新草稿”，以及报告数不增加 |

部分发送场景采用受控协程时钟，只发出固定样例 `abcdef` 的第一个按下报告，再编辑 `new draft` 并进入后台中止。返回时两份内容均保留，取消状态不恢复为发送，未累计/续发/重发。

**模拟边界：** Robolectric 的 startActivity/PendingIntent.send 记录 Intent，不能代替 Android 系统 task 管理器。测试检查真实入口启动契约，并显式执行 MainActivity 的 onNewIntent 恢复路径；它证明应用处理该恢复路径时保留状态，不能宣称系统已真实选择并复用旧 Activity。API 34+ TileService 的系统折叠/启动重载也使用测试 shadow 捕获 PendingIntent，未模拟 SystemUI。下面仍列最少真机步骤。

## 最少手机验收（未执行）

安装新 APK 覆盖更新现有 YoRemote，不卸载原版或清除其数据。测试时保持应用进程和任务存活，不强行停止、滑除任务或使用“不保留活动”；本修复有意不提供跨进程文本持久化。

1. 连接现有 Mac；添加 YoRemote 磁贴和桌面组件。快捷输入页编辑固定草稿 `nihao`，按 Home 进入后台，然后分别通过通知“打开”、磁贴、组件“打开”返回。每个入口检查仍在快捷输入页、草稿完整且未自动发送。
2. 用足够长的固定英文样例开始发送，期间编辑成另一份草稿后按 Home 中止；分别从三个入口返回。检查原提交文本与新草稿均可核对，Mac 可能已收到部分字符，但返回本身不继续/重发。
3. 如使用 adb，可在每次后台前和返回后读取 `dumpsys activity activities` 中 YoRemote 的 MainActivity task/ActivityRecord，确认没有被外部入口清空重建；同时观察内容和 Tab 保留。系统回收后的冷启动不属于此项内存保留保证。
4. 停止 YoRemote 的 HID 服务后，分别用未连接通知和组件“连接”按钮检查其启动同样不会清空仍存活的 Activity；没有现存 Activity 的冷启动应正常打开。

本轮不把上述 task/SystemUI/启动器行为标记为真机通过，也不重新开展原版 HID 轮换、中文候选或全库审计。
