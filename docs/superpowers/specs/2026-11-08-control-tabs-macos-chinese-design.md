# 四页控制与 Mac 中文输入设计计划

状态：2026-11-08 用户已批准按本设计正式实施，旧阶段的“整体待确认／仅修改计划”已结束。快捷输入为第三个独立页面；顺序为“触控板、键盘、快捷输入、遥控”。中文沿用已测可用的英文/拼音发送与 Mac 输入法组字；定制版基础包名为 `io.github.yohuohuohuo.btremote`，显示名称为 `YoRemote`，供原版与定制版共存对照。已完成本地实施与 APK 交付，36 项测试通过；lint 保留原有失败，手机/Mac 验收待执行。详见 [实施与验收](../../YoRemote实施与验收-2026-11-08.md)。

## 已确定的需求

1. Android 手机作为 Mac 的蓝牙键鼠，复用现有已完成连接测试的 HID 基础。
2. 原遥控、触控板、按键矩阵和快捷输入面板拆成四个平级页面，底部 Tab 顺序固定为“触控板、键盘、快捷输入、遥控”，点击切换，主要控制内容不再放在弹层中。
3. 触控板使用全部可用区域。按 2026-11-09 用户的新要求，键盘页面仍独占内容区，但竖屏矩阵固定为 320dp 并垂直居中，不再拉伸填满上下空间；横屏保留紧凑布局。
4. 中文优先沿用用户已测可用的快捷输入方式：手机输入框编辑英文/拼音，点击发送后逐字符模拟按键，Mac 的日常中文输入法完成组字、显示候选，再用控制按键或在 Mac 上选字。完整键盘页也保留逐键输入与选字能力。
5. 本轮不做手机端选好中文后整段发送，不启用 Unicode Hex Input，不开发 Mac 接收程序，不增加联网、剪贴板同步或输入法引擎。
6. 原作者 App 与定制版须能在同一手机共存安装；定制基础包名改为 `io.github.yohuohuohuo.btremote`，显示名称为 `YoRemote`，保留原版作为对照，不覆盖或卸载原版。

- 仅调整安装身份 `applicationId`，保留源码 `namespace`、Kotlin 包路径和组件类名 `com.atharok.btremote`，避免无关的全项目重命名。实施时同步修改根目录 `build.sh` 中的包名重写值和定制构建配置，确保从干净上游重放补丁后仍得到新身份，不被打包脚本还原。Android 区分安装身份与代码 namespace，参考：[Android 应用模块配置](https://developer.android.com/build/configure-app-module)。

- 新包名属于独立安装，不是旧测试 APK 的覆盖升级。用户保留原版及旧测试包；定制版首次运行需单独授权并配置应用内偏好/收藏，不做自动数据迁移。手机系统的蓝牙配对记录仍由系统管理，不因应用包名不同变成两套独立蓝牙设备，也不自动删除既有配对。

- 打包时检查合并 Manifest 的最终包名、组件、依赖生成的 provider authority 和测试 APK 身份；通知、快捷设置与桌面组件入口必须打开各自版本。当前主 Manifest 未声明固定 provider authority；不为可能的冲突预先增加配置，以实际合并结果为准。

## 用户测试基线与未确认事项

- 用户报告鼠标控制未发现问题；这属于用户当前测试结果，不等于所有鼠标功能已全面验收。后续鼠标改造以扩大布局为主，保留手势、指针速度和现有发送逻辑。
- 用户进一步实测：快捷输入框直接发送中文不行；Mac 切换中文输入法、手机输入英文并发送，可以触发 Mac 端选字，用户确认该功能正常。本轮将这条已验证的工作方式作为快捷输入页及中文使用流程的基线，不再把它列为“英文发送完全无效”的未决故障。
- 上述实测确认的是普通快捷输入的英文/拼音发送和 Mac 候选链路，不等于 Direct Input 边打边发、所有字符、所有 Mac 输入法或极端连续发送均已验证。当前 Mac 输入法具体类型尚未记录。
- 用户报告键盘输入不够流畅，有时需要点好几下才输入成功；已进一步确认发生在截图中的按键矩阵，直接点字母、数字等键，而非手机系统输入法的 Direct Input 或文本框“发送”入口。
- 现象的真实原因尚未复现确认。短按与慢按的差异、触摸事件与 HID 报告是否一一对应、`sendReport()` 是否返回失败、Mac 当前输入源和目标文本框均需在实施时记录。
- 优先处理键盘可靠性，再叠加键盘页面重排，避免布局变化掩盖原有漏输入问题。鼠标正常缩小了排查范围，但不能单凭这一点证明整个蓝牙链路无问题。

## 推荐交互

“全屏页面”指每页独占内容区，不再上下拼接或以底部弹层承载主要控制。状态栏、设备信息栏、底部 Tab 和系统手势安全区不计入可操作内容区；本轮不默认启用沉浸式隐藏系统栏。截图用于确认现有区域和组件身份，不按截图像素直接推导 Android dp。

共同结构：顶部显示当前 Mac 名称、连接状态与更多菜单；中间只显示当前控制页；底部固定为“触控板｜键盘｜快捷输入｜遥控”。沿用现有主题、图标和按键风格。设备名称过长时单行省略。

- 点击 Tab 切换，不增加左右滑动切页，避免与触控板手势冲突。
- 首次进入默认第一个 Tab“触控板”，之后在本次页面生命周期内保存当前 Tab；旋转不重置选择。不增加全局偏好设置。
- 设置、断开连接和帮助仍由更多菜单进入；删除原来与 Tab 重复的鼠标/键盘切换入口。
- 四页共用同一个连接状态、前台 HID 服务和 RemoteViewModel，不创建多套连接或四个 Activity。

| 页面 | 内容与尺寸策略 | 保留的操作 |
| --- | --- | --- |
| 触控板 | 主触控区填满剩余内容；右侧滚动按钮和底部鼠标键使用固定的适合手指触控的尺寸，不继续按屏幕宽高的 15%/20%放大 | 指针移动、单/双/三指点按、双指滚动、左中右键、原有拖动及陀螺仪选项 |
| 键盘 | 原高级键盘从弹层移到独立页，取消竖屏半屏高度限制，提供适合 Mac 的紧凑横屏排列 | 字符、数字、修饰键、方向键、Esc、Tab、退格、回车、F1～F12等原有按键；Mac 输入法组字和选字 |
| 快捷输入 | 原文本输入面板从底部弹层移到独立页，编辑区使用剩余可用内容；默认“先编辑，再发送”，适配手机系统软键盘 | 英文/拼音编辑与发送、现有空格/方向/退格/回车等控制；沿用 Mac 输入法候选流程 |
| 遥控 | 单独显示原控制页 1；在独立内容区重排间距，不再为触控板预留半屏 | 媒体、音量、数字和原有遥控按键；方向控制保留为该页的辅助入口 |

### 触控板细节

采用父容器实际可用尺寸填充，不再用整个屏幕高度猜测内容尺寸。侧边滚动按钮每个触控目标至少 48dp，底部鼠标键高度建议 56dp，主触控区吸收剩余空间。尺寸使用项目现有间距资源适配；不增加手势种类或改变指针加速策略。

### 键盘细节

2026-11-09 竖屏布局修订：用户已明确要求固定高度、上下居中。矩阵采用 320dp，在公共顶栏与底部 Tab 之间的可用内容区居中；此要求替代此前竖屏铺满矩阵的安排。用户随后要求四方向键在竖屏移到矩阵下方，按最后补充示意图排成中心留空的十字形，普通层空格扩展；小窗口保留滚动，横屏和按键行为保持原样。

- 竖屏仍可操作；在键盘页提供“横屏”入口，用户主动切换后仅该页使用横屏。离开键盘页恢复进入前的方向策略，不改变系统旋转设置。
- 横屏按常规键盘重新排布为约五行，保留常用数字、字母、编辑键和修饰键；F1～F12等扩展键通过明确的功能层入口访问。这里的“功能层”只在手机界面选键，不假装发送不存在的标准 Fn 修饰位。
- `Meta` 在面向 Mac 的界面标为 `⌘ Cmd`，`Alt` 标为 `⌥ Option`，保持现有 HID 语义。横屏不把原八行布局直接压进更短的高度；不足时优先调整紧凑工具栏/功能层，不能靠持续缩小触控目标解决。
- 完整键盘页保持纯按键操作，支持在 Mac 中文输入法下逐键输入拼音；不在该页嵌入文本编辑模式。先编辑再发送的工作方式由独立“快捷输入”页承载。
- 字母、空格、数字、方向键、退格和回车保持易于触达，用于控制 Mac 的中文候选窗口。按键矩阵发送的是物理按键，不把手机上的汉字反向转成拼音。
- 当前 Tab、功能层和方向选择在旋转中保留；按住状态不跨旋转保留。切换功能层前也要释放当前按键。

### 快捷输入细节

- 复用现有 `VirtualKeyboard.kt` 的文本编辑和字符转按键能力，提取可在普通内容区使用的组件，取消主要内容的 BottomSheet 包装，不重建输入法或另造一套文本传输。
- 默认普通发送模式：手机使用英文输入法或英文模式输入拼音，如 `nihao`，右侧发送按钮按既有 `shouldSendEnter=false` 路径发送。输入区提示“Mac 先切到中文输入法，手机输入拼音；不直接发送汉字”。
- 文本编辑区利用页面剩余空间；发送、清空（如需显式入口）和现有控制键保持可达。手机软键盘弹出时，处理 IME/系统安全区，确保输入框、发送入口、控制键与四个 Tab 不被遮挡或推到屏外。
- 该页以竖屏编辑为主并跟随系统方向；从完整键盘页切来时先恢复原方向策略，不继承该页临时的横屏锁定。旋转、切 Tab 或暂时收起软键盘不丢失尚未发送的内容。
- 沿用现有空格、方向、退格、回车等按钮控制 Mac 候选；数字可通过输入框发送或切到完整键盘页输入。不新增 Mac 候选回传或手机候选窗口。
- 普通发送不自动追加空格或回车，Mac 回车由独立按键显式触发。现有手机 IME“完成”会附加 Enter，与箭头发送不同；迁移时统一为普通发送语义，避免未选词时隐式提交/执行。
- 原有 Direct Input 开关可作为此页辅助模式保留，明确区分“先编辑再发送”和“边输入边发”，并保留发送按钮相应的可用状态；不能将用户对普通发送的确认外推为该模式已通过。仅做与页面迁移直接相关的回归，不借此扩大中文直传范围。
- 迁移时补齐既有发送相关的最小反馈：发送中禁用重复提交或提示忙；请求未受理、接口失败时保留内容；不可映射的汉字等字符在发送前提示并保留原文，不默默忽略。已完成蓝牙报告提交后，再按现有“发送后清空”设置处理内容；清空不被表述为 Mac 已成功输入。
- 切页、旋转、后台或断线中止本页未完成发送并尽力释放按键，保留供用户核对的原文，提示 Mac 可能已收到部分字符，不自动重发。复用现有发送任务与连接，不增加持久队列或后台重放。

## 中文最小实现

### 路线比较与选择

| 路线 | 组字和选字位置 | Mac 条件 | 最新决定 |
| --- | --- | --- | --- |
| 快捷输入发送英文/拼音，Mac 输入法组字 | Mac 候选窗口，可用手机控制键或 Mac 选字 | 使用日常中文输入法，如系统拼音 | 主路径；用户已实测普通发送可以触发 Mac 选字，迁移为独立页面，位于第三个 Tab |
| 完整键盘逐键输入拼音，Mac 输入法组字 | Mac 候选窗口，手机按空格/数字/方向键选择 | 使用日常中文输入法，如系统拼音 | 保留；按键矩阵漏输入问题独立诊断 |
| Unicode Hex Input 按键序列 | 手机选好字后再转换发送 | 添加并切换专用输入源 | 本轮移除，相关编码器、文本发送 UI 和测试不再纳入计划 |
| Mac 接收程序 | 可提供手机组字后发送等能力 | 安装接收程序并增加通信/权限设计 | 本轮不做 |

主流程：快捷输入页编辑 `nihao` → 点击发送 → 原有字符映射与蓝牙 HID 报告逐个发出 `n i h a o` → Mac 中文输入法显示候选 → 用手机控制键或 Mac 选择“你好”。完整键盘页可直接逐键完成相同过程。候选词显示在 Mac，不回传手机。Mac 切到 ABC 时，相同发送内容应得到字母；App 不检测或强制切换 Mac 输入源。

Mac 拼音候选的具体选择行为由用户所用输入法决定。系统拼音支持空格、数字与方向键等候选操作，实施时先以系统拼音作为验收基线，不声称所有第三方 Mac 输入法均已验证。参考：[Apple 中文候选窗口说明](https://support.apple.com/en-ie/guide/chinese-input-method/cim12992/mac)。

首版不新增 Unicode 转换、候选同步、手机输入法引擎或汉字直传。完整键盘按事件发按键，快捷输入复用既有英文/拼音批量转按键和发送节奏，不因页面迁移随意调整已测可用的参数；只有用户显式按下空格、回车等控制键才发送对应动作，不为拼音自动补选词/提交键。中文、标点、emoji 和生僻字是否能在 Mac 选出由 Mac 输入法能力决定，不再设置原 Unicode 方案的 BMP 字符范围限制。

快捷输入不是手机选好中文后直传，也不是剪贴板粘贴；手机系统输入法需保持英文/拼音字母输出，不能把已选好的汉字反向转拼音。普通发送已验证正常与完整键盘矩阵偶发漏输入是两项独立结论，不能因一条路径正常而把另一条标记为已修复。

## 键盘漏输入的诊断计划

### 已核对的代码事实

- `BasicButton.kt:34` 通过 `PressInteraction` 依次通知 `touchDown()`、`touchUp()`，Cancel 也调用 `touchUp()`。
- `AdvancedKeyboard.kt:111` 的普通字母/数字回调仅将 `keyByte` 改为按键值或零；实际蓝牙发送发生在 `AdvancedKeyboard.kt:87` 的 `LaunchedEffect(modifierKeyByte, keyByte)` 中，依赖 Compose 重组观察状态。
- Android 官方文档说明，Composition 按帧批处理；若状态在同一帧改变后又恢复，观察该状态的组件可能看不到中间变化。该机制与当前写法存在对应关系，可能解释短按“按下→抬起”未形成完整 HID 报告，但尚未在用户设备上证明就是本次根因。参考：[Compose 交互与同帧状态变化](https://developer.android.com/develop/ui/compose/touch-input/user-interactions/handling-interactions)。
- `MousePadLayout.kt` 的鼠标回调直接调用发送，不经过上述键盘状态驱动的 Effect。这是需要比较的路径差异，不能据此直接断言蓝牙完全正常。
- `RemoteViewModel.kt:48` 的键盘回调未向 UI 暴露 `sendReport()` 的成功/失败结果。因此仅凭当前界面反馈，无法区分未生成报告和接口拒绝报告。
- 已核对测试 APK 对应的临时源码：高级键盘文件与当前固定上游版本一致，以上不是尚未打包的定制代码。

### 诊断与验证顺序（进入实施阶段后执行）

1. 固定 Mac 文本编辑普通输入框，先选 ABC，记录手机型号、Android/macOS 版本、键盘布局以及快速轻点、稍慢点按、连续同键/不同键的差异；再切系统拼音比较。先把普通字母漏输入与候选词选择问题分开。
2. 用受控 Compose 帧时钟和可记录的发送回调复现“同帧按下再释放”，检查是否少了按下报告；同时覆盖连续同键、交替键、Shift+字母及触摸取消。先保留能在旧实现失败的用例，再修实现。
3. 在固定测试序列中记录触摸事件、键盘报告序号、相对时序和 `sendReport()` 返回结果，定位丢在 UI、报告生成还是蓝牙提交阶段。诊断不记录日常输入文本、完整输入历史或其他敏感数据，不做常驻遥测系统。
4. 若复现确认是 Compose 状态合并，最小修复方向为在按下/释放事件路径上立即、按序发送报告，界面状态仅用于显示，不依赖重组转发瞬时按键事件。先复用现有回调和 ViewModel，不预设新事件总线、持久队列或后台服务。
5. 若事件/报告均完整且接口接受，而 Mac 仍漏字，再验证 HID 按键持续时间/报告间隔及主机处理；只根据真机证据调整必要参数，不先全局加延迟、不自动重发按键。`sendReport()` 返回 true 不等于 Mac 已产生对应文字。
6. 如果共享 `BasicButton.kt` 确需修改，覆盖已知正常的鼠标点击和拖动回归；不要为了键盘问题重写正常的鼠标手势或更改指针策略。

停止条件：复现与修复回归证据一致，用户真实手机上的普通快点不再需要重复点击、连续按键不丢不重、释放与组合键正确。若缺少真机证据，应保留问题未解决状态；四页布局等独立工作可继续，但不能把漏输入标记为已修复。

## 必须随本次改造处理的按键语义

`AdvancedKeyboard.kt` 当前以 `keyboardKey is TextAdvancedKeyboardKey` 判断修饰键，但 `AdvancedKeyboardLayout.kt` 中 F1～F12 和 Esc 也属于这个显示类型。该条件会把这些普通按键编码到修饰字节；需改为显式的按键语义，不能依赖文字/图标外观，也不能仅靠 byte 数值识别（F7 与右 Alt 的值可能相同但含义不同）。

这是独立的键位语义问题，不足以解释用户报告的普通字母、数字偶发漏输入；不能只修 F1/Esc 就宣称本次漏输入已解决。

修饰键状态按位组合和清除；Tab 切换、功能层切换、旋转、触摸取消及离页时清理本地按住状态，并分别发送键盘、鼠标、消费控制的全释放报告，避免 Mac 端持续按住 Cmd、Option 或鼠标键。与断线有关的释放只能尽力发送，不能伪称已经送达。
